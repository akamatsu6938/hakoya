# 技術の選定と決めたこと

新しい順に上へ足していく。

## 2026-11-03 物件ごとの値は glb から、会社ルールは「glb のクセの直し方」と「模型の好み」
- **作者の考え（11/3）**：基礎高・壁厚は会社で同じだが、階高などは物件ごとに変わる。会社として新しい仕様の建物を建てるときにも使えるよう、**物件ごとに glb を見て決める方がソフトとして優れている**。最終的には、会社のルールを AI が言語化できるようにしたい。
- **決めたこと（いまの作りの確認と、これからの方針）**
  - 形の値（壁の位置・階・階高・天井高・開口・屋根）は、いつも物件の glb から測る。会社ルールの値は、glb にないときの予備と、違いを知らせる比べ用。
  - 会社ルールに残すのは、①glb（Walk in home）のクセの直し方（例：内壁は glb では仕上げ面の間 145 → 実際の 130 で作り直す、単独の壁の部品は 180 で入っている）、②模型の好み（屋根の出・ファジースキン・はめあい）。
  - ①の直し方も、できるだけ「物件の形から決まる決まり」にする（例：単独の壁の厚みは、片側が家の中かどうかで決める。数値を会社ごとに覚えさせない）。
  - いつもと違う値（会社ルールの選択肢にない階高など）は、勝手に直さず、知らせて人に聞く。
- **単独の壁の厚み**：片側が家の中（基礎の外形の内側でポーチ以外）・反対側が外なら外壁の一部 → 外壁の厚み。外の面はそろえたまま、内側の面を寄せる。両側とも外なら glb のまま。物件A の4枚で 作者の答えと一致（`adapters/walls.py` の `envelope_standalone`）。
  - 部屋の床（typeEHeya）だけで「家の中」を決めると、W12（窓際の腰掛けのくぼみの外の壁）が外・外に見えた。腰掛けの所は部屋の床がないため。
- **下がり壁**：床に届かず天井から下がっている内壁は屋根の部品へ。屋根の裏まで立ち上げ（ずれ止めの三角柱と同じ作り方）、天井より下は1階の壁をはめあいの隙間の分だけ広く抜く。物件A の W15 で、組んだときに重ならないことを検査で確かめた。

## 2026-11-02 囲んで直す（2D の平面図から）の作り方
- **囲みの中の部材はコードが決める**（`core/lasso.py`、SPEC §9-3）。
  - 壁：中心線のうち囲みの中の長さが、壁の長さの半分以上か 1,000mm 以上。長い壁の一部だけを囲んでも選べる。囲みの縁にかかっただけの直交する壁は選ばない。短い壁（約2m 未満）は、半分入れば選ばれる（物件Aで W12 を囲むと、隣の短い W4 も入った）。
  - 窓・ドア：中心が囲みの中。
  - 自分と交わる囲み（8の字）は直してから使う。
- **座標の受け渡し**：平面図の SVG に、mm への直し方（原点・縮尺・余白）を data-* で書き、画面が囲みの点を平面の mm に直して送る。どの部材かはサーバーが決め直す（画面の言うことは信じない）。
- **Claude に渡すもの**：囲みの中の部材の一覧（番号・種類・厚み・長さ・高さ）と一言。図は Claude が必要なら render_view（平面、囲んだ部材を赤枠）で見る。SPEC の「囲みを描いた画面の画像」の代わりに、囲んだ部材の強調で伝える（囲みの線そのものは描かない）。
- **Claude が返すもの**：検品と同じ道具の propose_override（直す案）か ask_question（質問）。質問の選択肢を押すと、答えを添えてもう一度頼む。
- **承認**：画面から受け取った数値は使わず、サーバーが出どころ（value_source）から計算し直してから、修正として1件記録する（origin は lasso）。
- **つなぎ方**：claude_code（Agent SDK、1人の担当、サブエージェントなし）／api_key（Messages API、検品と同じやりとりの回し方）／off（Claude を使わず、囲んだ部材の表の行に色を付ける）。1回の上限はやりとり 10 回・$1（`limits.lasso_*`）。
- **記録**：1回ごとに一言・囲んだ部材・直す案・質問・費用を `lasso_log.jsonl` に残す（SPEC §7-5「手直しの1回あたりの費用を記録」）。
- **待ち方**：検品と違い、答えが返るまで画面で待つ（裏で動かさない）。囲んで直すは1人の担当なので短い（推定 30秒〜2分）。
- **まだ確かめていないこと (要検証)**：本物の Claude での答えの当たり具合と時間・費用（利用枠を使うので、この間は試していない）。3D で囲んで直すは、まだ作っていない。

## 2026-11-02 api_key 接続（社外用）の作り方
- **決めたこと**：Client SDK **anthropic 2.3**（Messages API）で、claude_code 接続と同じ動き（6つの面の検品担当を同時に回す → まとめ役が JSON にする）を作る（`core/ai/api_runner.py`）。API キーの保管は **keyring 25.7**（Windows では資格情報マネージャー）。
- **理由**
  - 社外用の exe では、利用者の Claude のプランを使えない（SPEC §7-4）。API キーで動かすには Messages API を直接呼ぶのが一番素直。
  - anthropic と keyring は、どちらも Python 3.14（Windows）で入ることを確かめた（2026-11-02）。keyring は Windows の資格情報マネージャーをそのまま使える（自分で暗号化を書かなくてよい）。
- **作り方の決めごと**
  - **道具を使うやりとりは自分で回す**（SDK の「道具を回す係（tool runner）」は使わない）。tool runner はまだ試験版（beta）で、HAKOYA の道具の呼び出し（`call_tool`）・画像の返し方・費用の上限を細かく決めたいため。
  - **Skill の文章を指示（system）として渡す**。Agent SDK の Skill の代わり。面ごとの担当は全員同じ指示・同じ道具の並びにして、「覚えておく印」（プロンプトキャッシュ）を指示の終わりとやりとりの最後に付ける。2回目からは、覚えた部分を1割ほどの料金で読み直せる。
  - **まとめ役は構造化出力**（`output_config.format`）で、決めた形の JSON を返させる。決めた形（FINDINGS_SCHEMA）は、構造化出力の決まり（すべての object に `additionalProperties: false`、型の並びは anyOf）に合わせてコードで直してから渡す。
  - **費用は返事ごとのトークン数から計算**する。料金表は `rules/ai_models.yaml` の `prices_usd_per_mtok`（変わったらここを直す）。上限（`limits.max_budget_usd`、いまは $3）に達したら、次の呼び出しの前に止める。面ごとのやりとりは 12 回まで（`limits.max_turns_per_face`）。
  - **流しっぱなし（streaming）にはしない**。1回の返事の上限を 16,000 トークンにしているので、ふつうの呼び出しでも時間切れにならない。
  - **1つの面が失敗しても、残りの面の報告でまとめる**。全部の面が失敗したとき（キーの誤りなど）と、費用の上限に達したときは止めて、日本語で知らせる（API の英語のメッセージは記録にだけ残す）。
  - **キーは環境変数から読まない**。設定画面で入れたものだけを使う。画面には「保存してあるかどうか」だけを返し、キーの一部も出さない。
  - **ほかのサイトからの操作を止める**：書き換える操作（GET 以外）は、Origin（どのページから来たか）が HAKOYA の画面のときだけ受け付ける。ほかのサイトを開いたブラウザから、勝手に検品（料金がかかる）を始められないようにするため。
- **選ばなかったもの**：「拒否されたときに別のモデルで答え直す」機能（試験版）は入れていない。
- **まだ確かめていないこと (要検証)**：本物の API キーでの呼び出し（費用・時間・指摘の当たり具合）。偽の相手を使う試験だけ通っている。

## 2026-11-02 exe の作り方（一度目の試し）
- **PyInstaller 6.22 のフォルダ形式（onedir）**。1つのファイルにまとめる形（onefile）は、起動のたびに一時フォルダへ展開して遅く、ウイルス対策ソフトにも止められやすいため。設定は `packaging/hakoya_self.spec`。
- **データの置き場所**：exe のときは exe の隣の `data\`（`HAKOYA_DATA_DIR` で変えられる）。同梱物（rules・skills・画面のファイル）は exe の中から読む。
- **大きさ**：自分用で 421MB（Claude Agent SDK に同梱の Claude Code 本体が 335MB）。社外用（api_key と off だけ）は Agent SDK を外すので、ずっと小さくなる見込み（推定）。
- **口の番号**：既定 8765、`HAKOYA_PORT` で変えられる。すでに使われていれば、起動せずに日本語で知らせる。

## 2026-11-02 模型の組み立て方（core/builder.py）
- **寸法**：実寸 mm のまま組み立て、書き出すときに 1/50 にする。模型寸法の値（最小の太さ・三角・隙間）は実寸に直して使う。
- **パーツ**（平屋）：基礎／1階（床・内壁）＋1階の外壁（同じオブジェクトの別の部品。外壁だけファジースキン）／屋根（裏返して印刷 → ★2026-11-04 から面ごとに上の面を下に寝かせる。下の「屋根の印刷」）／ポーチの天井（平らな板）。
- **仮の決め（作者に確認する）**：ポーチの上の垂れ壁と、家の外に立って屋根まで届く袖壁は**屋根のパーツに付ける**。屋根は裏返して印刷するので、垂れ壁が支えなしで立つ。ポーチの天井の板は、垂れ壁の下まで広げ、その上に垂れ壁が乗る。
- **壁の高さ**：外壁・袖壁は屋根の下の面で切る。内壁は天井まで。開口の上（下）に残る壁が最小の太さ（模型1mm）未満なら、上（下）まで抜く（SPEC §8）。
- **基礎**：外周の帯（150、推定）＋内壁の下の帯。中は空ける。ポーチ・土間・袖壁の下も基礎のパーツ。土間は壁の下まで100mm広げて帯とつなぐ。
- **位置合わせ**：屋根の裏に三角（外壁の内側の角で四隅に近い4か所、はめあいの隙間だけ小さく）。基礎の帯の内側の角に地面から立ち上がる三角柱、1階の床裏に受けのくぼみ（隙間だけ大きく、深さ1.5mm、推定）。
- **窓の枠**：太さ＝最小の太さ、奥行き＝壁の厚みの半分（壁の真ん中）。引き違いは中央に縦桟、FIX は枠だけ。枠は「床・内壁」の部品に入れる（外壁の部品だとファジースキンが枠にもかかるため）。
- **scipy を使わない**：trimesh の一部の機能が scipy を要求したため、塊の数は manifold3d の decompose、GLB の色は材質の色、法線は画面側で計算にした（exe を軽くするため）。
- **3MF の置き方**：1つ目のオブジェクトは造形範囲の真ん中、2つ目からは横（範囲の外）に並べる。Bambu Studio の「並べる」で各プレートに配置する想定（要検証）。

## 2026-11-02 立体づくりと書き出しのライブラリ（11/4 の組み立ての準備）
- **決めたこと**：立体づくりは **manifold3d 3.5.4**、STL・GLB の書き出しは **trimesh 5.2.0**、3MF は **自前で書く**（標準の zipfile と XML）。
- **理由**
  - manifold3d：ブーリアン（合体・くり抜き）の結果が必ず閉じた立体になる作り。入力がすでに平面の多角形と平面の式なので、押し出し（`CrossSection.extrude`）と傾いた面での切断（`trim_by_plane`）で足りる。Windows・Python 3.14 用の完成品がある（約1MB）。Apache-2.0。
  - 3MF を自前で書く：Bambu Studio の部品ごとの設定（外壁だけのファジースキン）を `Metadata/model_settings.config` に入れるため。trimesh の 3MF 書き出しには追加のファイルを入れる口がない。
- **選ばなかったもの**：build123d / CadQuery（OCCT）。正確だが重く（数十〜数百MB）、exe が大きくなる。CadQuery は依存の casadi に Python 3.14 の Windows 版がない。lib3mf は 3.14 用の明示的な版がない。
- **確かめたこと**：入れて試した。壁を押し出し、窓をくり抜き、勾配0.15の面で上を切ると、エラーなしで閉じた立体になり、体積も手計算と合った（0.7627m³）。
- **まだ確かめていないこと**（調べ物のサブエージェントの報告による。推定）：自前の 3MF に書いた `fuzzy_skin=external` が、Bambu Studio の画面で部品の設定として出て、スライスに効くか。Bambu Studio で実際に開いて確かめる。

## 2026-11-02 開口と屋根の読み方（段階2c）
- **開口の穴**：建具の部位のうち、取っ手（HTOT・DTOT・TOT1〜3）と吊り戸のレール（OSTN）を除いたものの範囲。平面の形は、床の高さに敷居（KURI）があれば敷居、なければ残りの部位を囲む最小の長方形。★壁の外に吊る引き戸はレールが穴の約2倍あるため。
- **どの壁の穴か**：穴の平面の形といちばん重なり、高さも重なる壁。壁の始点からの位置（offset）と幅は、穴の形を壁の向きに投影して出す。
- **種類**：TOT・EHN1 があれば玄関ドア。下端が FL+100 以下ならドア（OSTN＝吊り引き戸、DTOT＝開き戸、SDOR 2枚＝引き違い戸）。それ以外は窓（MADO 2枚＝引き違い、0枚＝FIX、1枚＝形不明）。
- **高さ**：絶対の高さ（sill_mm・head_mm）と、FL からの高さ（sill_fl_mm・head_fl_mm）の両方を持つ。図面の注記（FL+2000 など）と照らし合わせやすくするため。
- **屋根**：YANE_MAIN（上の面）と YANE_NURA（下の面）をそれぞれ平面に当てはめる。ずれが5mmを超えたら片流れでないとして `unknown`（SPEC §1：片流れ以外は対象外）。厚みは面に垂直な長さ。東西南北は glb の +Y を北とみなす（推定）。
- **軒の出**：屋根板の範囲と外壁の外形の差。軒樋を含めた値も別に持つ（★物件Aの146mmは軒樋だった）。

## 2026-11-02 壁の作り直し方（段階2b）
- **壁の持ち方**：SPEC §6 どおり「中心線（始点・終点）＋厚み」。加えて `bottom_mm`（下端）と、外壁は `top_glb_mm`（glb の面が届いている上端）を持つ。★物件Aには、ポーチの天井（2,824）から屋根までの垂れ壁があり、床から始まらない壁があるため。
- **外壁**：外壁の面を「同じ向き・同じ位置」でまとめ、位置ごとに縦に切って下端を測る。下端が FL+300 より上で、開口（建具の箱）でもない所は「途中から始まる壁」として分ける。帯は面から内側へ外壁の厚み。入隅は厚み分伸ばして埋める。
- **背中合わせの外壁**：間が外壁の厚みの2倍より近く、300mm 以上重なるとき、**内壁**（会社ルールの厚み・天井まで）として作る。★物件Aで 作者確認：「外壁ではなく内壁」。向かい合う仕上げ面から作った内壁で覆われていれば、そちらにまとめ、`glb_exceptions` に記録する（検品の材料）。窓と窓の間の柱型の脇の面（162mm）は重なりが短いので対象外。
- **縦の抜け（開口）**：向かい合う仕上げ面を何か所かで縦に切り、壁の全長にわたって 300mm 以上面のない高さがあれば、壁を上下に分ける。★物件Aのカウンター沿いは FL+2200 の下がり壁と腰掛け（作者確認）。カウンター（typeEKaun）と重なる低い部分は造作として省く。高さの違う壁は、つないだり「覆われている」とみなしたりしない。
- **上がり框**：typeEAgar の位置にできる隙間は壁にせず、未解決にもしない（★作者確認）。
- **壁の端を長く伸ばすとき**：伸ばす先に平行な壁がすでにあるなら伸ばさない（少しずれた位置の本来の壁を覆って消してしまうため）。
- 作者の答えは `rules/answers.jsonl` に残す（SPEC §9-1）。
- **単独の壁**：垂直な面の面積が 0.05m² 以上かつ高さ 300mm 以上のものだけ。平面の形は部材全体を囲む最小の長方形（斜めでもよい）。
- **内壁**：SPEC の手順で内壁の範囲を出し、向かい合う仕上げ面（間 80〜270mm）の真ん中を中心線にする。厚みは会社ルール（130）。同じ線の上の壁は、間が内壁の範囲かドアの位置ならつなぐ。端はぶつかる壁の中心線まで伸ばす。
- **使わない面**：巾木・廻り縁（SPEC どおり）と、床から300mm以下しかない面（★上がり框の段）。
- **向かい合う面のない内壁の範囲**：壁にはせず `unresolved` に出す（SPEC §2-5）。
- **斜めの壁**：どの手順も面の向きだけで決めるので同じ式で扱える。架空の家を30度回したテストで確かめた（実物での確認は斜めの壁の物件が手に入ってから）。
- **確認用の画像**：開発中の確認に Pillow を .venv に入れた（ソフトの部品一覧にはまだ入れない。検品の画像づくりで使うときに改めて決める）。

## 2026-11-02 高さの決め方（段階2a）
- **GL**：敷地（typeESiki）の高さ。敷地がなければ Z 0 とし、`gl_assumption` に残す。
- **基礎天端**：基礎の本体（KISO_HONT）の側面が届いている一番上。★物件Aでは天端の水平な面が KISO_ILOW に入っていて、水切り（KISO_DMIZ）は 510 まで出ているため。
- **FL**：部屋の床（HEYA_YUKA・SHUU_YUKA）の水平な面で一番多い高さ。床の高さが 1,500mm 以上離れていたら別の階とする（2階建ては物件Bで要検証）。
- **天井高**：その階の床とすぐ上の階の床の間にある天井（HEYA_TENJ）で一番多い高さ − FL。
- 出力では、glb の元のファイル名ではなく「物件A.glb」と書く。ノード名もそのまま出さない（家具のノード名には部品のパスが入るため）。種類のコードとノード番号だけを出どころにする（例：`glb:typeEHeya#15`）。

## 2026-11-02 glb の読み取りと平面の計算に使うライブラリ
- **決めたこと**：glb の読み取りは **pygltflib**、座標の計算は **numpy**、平面（2D）の計算は **shapely 2**、設定ファイルは **PyYAML**、テストは **pytest**。
- **理由**
  - pygltflib：ノード名（`typeE○○`）・行列・マテリアル名（部位のコード）・Walk in home の付加情報（`WIH_version_info`）を、glb の形のまま取り出せる。部材ごとの「出どころ」（`glb:typeETate#27`）を正確に残すのに向いている。
  - shapely 2：SPEC §4-1 の壁の作り直し（帯にする・合わせる・膨らませて縮める）が、そのまま関数の呼び出しで書ける。斜めの壁も同じ書き方で扱える。
- **選ばなかったもの**：trimesh（glb の読み取りに使うと、部材をまとめたり名前を付け替えたりするため、出どころを追いにくい）。3D の立体づくり（11/4〜）では改めて比べる。
- **確かめたこと**：どれも Python 3.14（Windows）用の完成品（wheel）があり、入る（2026-11-02、pip で確認）。

## 2026-11-02 開発の見張り（フック・pre-commit）
- **決めたこと**：Claude Code のフックは Python で書き、`.venv` の Python で動かす。git の pre-commit は `.githooks/` に置き、`git config core.hooksPath .githooks` で有効にする。
- **理由**：PowerShell と Git Bash の両方から同じように動き、テスト（pytest）で「本当に止まるか」を確かめられる。`.git/hooks` はリポジトリに入らないため、`.githooks/` に置いて2台の PC で共有する。
- **止める範囲**：見張り（書き込む前）は「glb・jww への書き込み」「data/ の中への書き込み（local_paths.yaml だけは例外）」「git add -f と data/・glb・jww・3mf の追加」。pre-commit は「data/・図面・模型・画像ファイル」「ng_words の言葉」「API キーらしき文字列」。
- **出してはいけない言葉**：`data/local_paths.yaml` に `ng_words:` の一覧を足した（SPEC にない項目）。検査で見つけても、言葉そのものは画面に出さない。

## 3D で囲んで直す（2026-11-03）
- **選び方：部材ごとの当たり判定用の形を色で塗り、画素を数える（GPU で選ぶ）。** 3D の模型は部品ごとの形で、壁や窓の番号を持たないため。
  - 当たり判定用の形はサーバーが building.json から作る（`core/pick.py`、組み立てと同じ道具。修正を当てた後の家）。
  - 画面は、見えている部品の奥行きを先に描き、その上に当たり判定用の形を描く。画面に見えている部材だけが数えられる（SPEC §9-3「画面に映っている部材の割り出し」）。番号は頂点の色で入れる（three.js の色の変換を通らず、番号がそのまま戻る）。
  - 画面は画素の数を送るだけで、選ぶかはサーバーのコードが決める（テストで確かめられる）。
  - 選ばなかった案：光線を飛ばして当たりを調べる（部品の三角形が多く遅い）、点を画面に写すだけ（後ろに隠れた部材まで選ぶ）。
- **軒の出を直すと模型に効くようにした。** いままで軒の出は記録だけで、屋根板は「屋根の形＋板金の分」を4辺同じに作っていた。
  - 修正を当てるとき、直す前の glb の軒の出を `eave_glb_mm` に控え（building.json には入れない）、組み立てで差の分だけ、その向きの辺を動かす（`slab_outline`。L字のへこみの辺も同じ向きなら動く）。修正がなければ今までと同じ模型。
  - 区域B（2階建ての1階の壁の高さを決める範囲）とずれ止めの三角は、元の屋根の形のまま。
  - 大屋根は roof と roofs の2つに同じ修正を当てる（平屋の組み立ては roof、2階建ては roofs を読むため）。入れ子の項目は dict を作り直して書く（メモリ上で同じ dict を共有していることがあるため）。
- **Claude の number は人の文章にある数値だけ。** 囲んで直すでは、一言（と質問への答え）にない数値の案はコードが断る。図面の寸法は、jww を読めるまで人が書く。

## 会社ルールの言語化（2026-11-03）
- **目的（作者）**：「家・会社によって可変的な部分は模型ごとに変わるから物件ごとに変更する。ただし、壁厚や細かいルールなどがあれば、それは会社ルールとして残しておくことで、困った時の予防として利用できるようにする」。
  - 最初の計画（学んだ値で模型の作り方を変える）は、この言葉を受けて「予防に使う」中心に組み直した。
- **集計はコード、言葉は Claude、入れるのは人の承認だけ。** 数値（「2件中2件で 480」など）はコードが書き、Claude は根拠（集計の id・答えの id）を選んで文にする。文の中の数値が根拠にないと、コードが断る。
- **学んだルールは DATA_DIR に置く**（exe では rules/ に書き込めない。元の yaml の★のコメントを守る）。読み込むときに、学べる項目だけ型を確かめて重ねる。テストと控えの道具では使わない（HAKOYA_LEARNED_RULES=off）。
- **学べる項目**：基礎・1FL・天井高・階高の選択肢・外壁の厚み・ドアの上端・屋根の厚み。模型の作り方（model.*）・内壁の厚み（作者の決め）・窓の上端（家ごとに変わる）は学ばない。
- **予防の比べ**は、組み立てたときの rule_checks ではなく毎回いまの会社ルールと比べ直す（学んだルールも効く）。家ごとに変わる値（窓の上端・勾配・軒の出）は比べない。
- 選ばなかった案：yaml を直接書き換える（コメントが消える・exe で書けない）、そろえた後の値で数える（循環する）。

## 組み立てたら自動で検品（2026-11-03）
- **設定タブで選ぶ。既定は「コードの検査だけ（AI なし）」。** 組み立てるたびに勝手にプランや API の利用枠を使わないため。Claude（自分のプラン）を選ぶと、組み立ての後に確かめの窓を出さずに検品が始まる（自分で選んだ設定なので）。
  - 設定は `DATA_DIR/settings.json`（秘密でないものだけ。API キーは資格情報マネージャーのまま）。
  - 社外用の exe ではプランの接続を選べない（規約。SPEC §7-4）。API キーを選ぶときは、1回だけ費用の上限を見せて確かめる。
  - 検品中は組み立てを断る（検品が見ている模型が途中で変わらないように）。
- 選ばなかった案：既定を Claude にする（知らないうちに利用枠を使う）、サーバーが組み立ての中で検品を始める（テストで勝手に Claude が動くおそれ。画面が始める形にした）。

## 検品の当たり具合の試験（2026-11-03）
- **間違いは修正（overrides）で入れる。** 修正は組み立て・検品の図・Claude の道具のすべてに効くが、Claude には「修正した」とは見えないため。
  - 軒の出は使わない（人の修正どおりという注意書きが Claude に伝わる）。
- **判定はコード（`core/seeded_score.py`）。** Claude に採点させない（同じ Claude が自分の答えを甘く見るおそれ。何度やっても同じ判定になるように）。
  - 1つの間違いを何件で言っても「見つけた」は1件。間違いを入れる前の試しでも出た指摘は「もともとある」で、誤りに数えない（物件A にもともとある本当の食い違いで、試験の点が下がらないように）。
- **試験は一時フォルダで動かす。** 本物の修正・控え・学んだルールを変えないため。終わったら消す（glb の写しと場所が入るため）。
- **答えを教えない。** 検品の Skill の例文にあった物件A の番号（O4・W3）は「O○・W○」に直した。試験の番号や値が Skill・指示に入っていないことをテストで確かめる。
- **目標は変えない（最初の結果を見て）。** 最初の結果は 9/10・誤り1 で目標（7件以上・誤り3件以下）を超えたが、1回だけの結果で、Claude の答えは毎回少しずつ変わるため。


## 表で直す：階の高さ（2026-11-03 夜。作者不在のため、ふつうの考え方で決めた (推定)）
- **修正の相手は `level:1F`・`level:2F`、項目は `fl_mm`（GL から）と `ceiling_mm`（床から）だけ。** 階高は「2階の床 − 1階の床」なので、記録は 2階の `fl_mm` で残す（表には階高で出す）。
- **床を上げ下げしたら、その階と上の階のものを全部同じだけずらす。** building.json の高さはほとんど絶対値なので、当てるときにコードがずらす。基礎・外壁の下端（基礎の上から立つ）・ポーチ（地面の上）はそのまま。土間は同じ階の部屋なので一緒に動く。
  - 選ばなかった案：床だけ動かして屋根を残す（天井がつぶれ、壁が屋根を突き抜ける）。
- **天井の高さは、天井まで立っていた壁の上端だけを動かす。** 屋根は動かさない。
- **保存の前に、写しに当てて確かめる。** 家全体を見ないと決まらない（天井と屋根の間、上の階の床板、窓の上端）ので。もともとある食い違い（glb の例外）では断らない。
- **壊れた修正で画面が開けなくならないように。** 当てられない修正は飛ばして一覧に出し、組み立てに失敗したら足したばかりの修正を取り消す。

## 片流れ以外の屋根（2026-11-03 夜）
- **屋根を「面の集まり」で持つ。** 面ごとに平面の形と式を持ち、上から見た平面を面ごとの受け持ちの範囲に分けて、範囲ごとにその面の式で切る。
  - 理由：切妻・寄棟・L字の谷・入母屋に近い形まで、同じ作り方で扱える。屋根の形を自分で作る（屋根の形を外形から計算する「ストレートスケルトン」など）より、glb にある本当の面を使う方が、Walk in home の形とずれない。
  - 受け持ちの範囲の外周の帯は、角で留め（マイター）に分ける。勾配がそろった屋根では、隅棟・谷の線の延長と一致するので、軒の出を伸ばしても板がずれない。
  - 選ばなかった案：全部の面の「いちばん低い所」を屋根にする（切妻・寄棟は正しいが、L字の谷で壁を削りすぎる）／屋根の形をこちらで作る（実物の glb と合わない形になるおそれ）。
- **片流れはいままでの道のまま。** 面1つなら planes を持たず、組み立ての道具には平面の式（dict）をそのまま渡す（物件A・B の模型と控えが変わらない）。
- **面の分け方**：向き 2° 以内・高さ 20mm 以内を同じ面、0.1m² 未満は面とみなさない（物件A の屋根板は約100mm 厚・片流れで、Walk in home の面は平らに書き出されていた (推定でほかの形にも当てはめた。要検証)）。

## 表で直す：屋根の形（2026-11-03 夜。(推定) で決めた。作者に確かめる）
- **項目は 勾配 `pitch`（10 に対する値）・低い側 `low_side`・軒先の高さ `eave_tip_mm`。** どれも面の式から計算で出し、当てるときにコードが面の式を作り直す（building.json の pitch・low_side は名札だったので、変えても模型が変わらなかった）。
- **勾配は軒先を固定して回す。** 「高さ」は軒先（屋根の上の面のいちばん低い所）。図面の軒高（敷桁の上端）とは違うが、模型にあるもので測れる高さにした。
- **面が複数の屋根は、勾配がそろっているときだけ勾配を直せる。** 軒先からの高さを比例で伸ばすと、棟・隅棟・谷の平面の位置が変わらないため。向きは片流れだけ（切妻の棟の向きを変えるには面を作り直す必要がある）。
- **屋根まで届いていた壁はついていく。** 数値の高さの単独の壁（物件A の W11・W13 など）は、屋根の下の面から 150mm 以内に上端があれば「届いている」とみなす。

## jww の読み取り（2026-11-03 夜）
- **ライブラリは ezjww 0.7.6**（SPEC §4-2 で検証済み。pyproject に足した）。ネイティブ記録を使い、DXF には変えない。
- **表題欄は2つの決まりで読み捨てる**：用紙の下の帯（下端から 45mm 以内で、用紙の幅の8割より長い水平線のいちばん上より下）と、縮尺1の層（枠・表題欄）。用紙の外の文字、ng_words を含む文字も捨てる。読み捨てた文字はどこにも残さない（数だけ）。
- **位置合わせは「壁の面に乗る線の割合」で決める。** 寸法の数字に頼らない（Walk in home の書き出しや設計事務所ごとに寸法の入り方が違うため）。合わないときは合わせない（照合もしない）。
- **注記と開口は、近い順に1対1で結ぶ**（同じ窓に2つの注記を結ばない）。結べない注記は「要確認」として出す（図面だけにある窓の見落としに気づけるように）。

## 実物の切妻・寄棟（2026-11-03 深夜、物件C・D）
- **★Walk in home は切妻・寄棟の屋根を、面ごとに別の部材（typeEYane）で書き出す。** 部材ごとに上の面（YANE_MAIN）・下の面（YANE_NURA）・破風・鼻隠し・樋がある。
- **平面で 50mm 以内に接し、高さの範囲が重なる屋根の部材を1つの屋根にまとめる**（`merge_roof_parts`）。面に分けるのは前からの `detect_roof`。下屋と大屋根は高さの範囲が重ならないのでまとめない。片流れ（部材1つ）は今までどおり。
- 平屋で、まとめても屋根が2つ以上残る家（離れたポーチの屋根など）は、いまも1つ目だけ読む（要検証。まだ例がない）。

## 組み立ての後始末（2026-11-03 深夜、物件C〜F。(推定) で決めた。作者に確かめる）
- **離れた基礎の帯は、床下の見えない帯でいちばん近い帯につなぐ。** 幅は基礎の帯と同じ 150、高さは基礎の天端まで（床の板の下に隠れる）。土間（低い床）の下は通さない（帯が床から出てしまうため）。つなげないときはそのまま（検査の注意が残る）。理由：ほかの壁とつながらない内壁（収納・台所の壁）の下の帯が島になり、印刷すると基礎の部品がばらばらになるため。
- **1階のいちばん大きい塊の 1% より小さく、離れたかけらは作らない**（物件D の土間の穴の間の床の切れ端）。印刷すると置き場所の分からない小さな部品になるため。
- **基礎と1階が重なる所は、基礎の方を削る**（物件C：基礎の天端 480 より高いポーチ 500 に外壁の下端がめり込んだ）。1階の部品は見える部分なので形を変えない。
- **背中合わせの外壁の面が単独の壁に覆われていれば、単独の壁だけを作る**（物件E のポーチの袖壁）。
- **ポーチの天井の板は、天井につながる分だけ作る。** 垂れ壁の真下だけの板は作らず、その垂れ壁は自分の下端から作る（角だけで接すると閉じた立体にならないため）。

## 図面の照合：連窓・段窓（2026-11-03 深夜、物件F）
- **1つの品番が、glb では横に並ぶ連窓や上下に並ぶ段窓になることがある。** 幅はその開口か連窓、高さはその開口か段窓、上端はその開口か段窓のいちばん上のどれかで合えば一致とする。横に並ぶ窓の上端を連窓でまとめると、1つだけ下がった上端を見逃す（試験の E01）ので、上端には使わない。
- **平面で重なる2つの開口（上下に並ぶ窓）は、注記の FL+ と上端が近くなる方に結び直す。** 離れた開口どうしは距離だけで結ぶ（間違いを隠さないため）。

## glb にありえない形を見つける（2026-11-03 深夜）
- **見つけるだけで、直さない。** 「glb の整合性（要確認）」として AI なしの指摘に出す。Claude への指示には入れない（検品の当たり具合を変えないため）。直し方は 作者と決める（docs/proposal-glb-consistency.md）。
- 決まり（物件A〜F で決めた）：平行な壁が厚みの中で 300mm より長く重なる／開口が壁の端から 20mm より出る（窓、または出た所に別の壁がある戸）／同じ壁の開口が横・縦とも 50mm より重なる／開口の上端が壁の上端・屋根の下の面を 50mm より超える／長さ 100mm 未満の壁。
- 拾わないもの：引き込み戸が壁のない隙間へ出る（物件B の O17）・連窓の枠の 25mm の重なり（物件F）・天井までのドアと天井の 30mm 下で終わる内壁の差（物件C・F）。

## 物件の登録（2026-11-03 深夜）
- **local_paths.yaml の最後に書き足すだけ。** 読み直して書き戻すと、作者のコメントや並びが消えるため。書く前に、足したあとの全体が YAML として読めるか確かめる。
- **出してはいけない言葉は物件ごとに持つ**（`物件X: {ng_words: [...]}`）。全体の ng_words と合わせて見張る。
- **Windows の「選ぶ」窓は PowerShell で出す**（tkinter は exe から外してあり、足すと大きくなる）。出せないときは場所を貼り付ける。
- **選んだ場所はサーバーの中だけで持ち、画面には番号と種類だけ渡す**（場所やファイル名に施主名が入ることがあるため）。
- glb にはファイルか、glb が1つだけ入ったフォルダを書ける。図面は、jww: の指定がなければ名前（平面・2階・立面・断面）で分ける。同じ種類が2つあれば使わない（取り違えないように）。

## まとめて検査する道具（2026-11-03 深夜）
- **本物の data/out に組み立てる**（画面の「読み込んで組み立てる」と同じ。番号は前回から引き継ぐ）。終わったあと、画面ですぐ見られるようにするため。
- **指摘（findings.json）は保存しない。** Claude の指摘と、人の判定を上書きしないため。AI なしの指摘は数えて表に出すだけ。
- **表には数・種類・番号と、HAKOYA が作った文だけを出す。** glb や図面の中の文字・元のファイル名は出さない。エラーの文も、場所の文字が入りそうなものは出さない（種類とコードの場所だけ）。

## 見直しのあとの決まり（2026-11-04 朝。サブエージェント3人の見直しから）
- **屋根の部材は、棟・隅棟・谷を共有する（上の面が同じ高さの頂点を2つ以上、間が 100mm 以上で共有する）ものだけをまとめる。** 前の「平面で 50mm 以内・高さの範囲が重なる」は、並んだ別々の下屋や庇までまとめた。物件C・D の面は頂点を共有していることを確かめた。

## 屋根の印刷：面ごとに分けて、上の面を床に付ける（2026-11-04）
- 作者：「印刷範囲が入らない場合は、屋根の線で分けるのはどうかな。…接着剤で付けてっていう方が割れ目も見えなくていい」「屋根形状によって、最適な印刷方法にすればいい」。

- 「図を見る」の図は、模型が新しくなっていたら作り直す。作り直せないときは前の図を使う。
- アプリの Claude の道具（Agent SDK）にも、返す前の出してはいけない言葉の検査を足した。思いがけないエラーは種類だけ返す（SDK は例外の文をそのまま Claude に渡すため）。

## 社外の Claude Code から HAKOYA を動かす（MCP の外部公開。2026-11-05）
- **作者「一通り全部」**：他社用の HAKOYA を使う会社の人が、自分の Claude Code を MCP でつなぎ、物件を見る・検品・直す案・指摘を送る・承認／却下・修正と取り消し・組み直し・書き出し・画面で開くまでを行う。説明は docs/mcp.md。

## 公開するものの呼び名と、公開の前の最終チェック（2026-11-05 作者）
- 公開するものは、すべて個人や会社を特定できない呼び名にする。社名・地域は出さない。前の版の文書にあった作者の紹介は誤りなので、どこにも書かない。
- コードの会社の呼び名を jisha（自社）に変えた（前の呼び名は社名に近いため。own は起動の名前とぶつかるので使わない）。画面の表示名も「自社」。前のデータは控えを取ってから一度だけ書き換えて、コードに古い呼び名を残さない。
- 提出用の書き出しで、作者の名前 →「作者」、ユーザー名入りの場所 →「%USERPROFILE%」に置きかえる（手元のリポジトリの記録はそのまま）。置きかえのあとに名前・ユーザー名・誤った紹介の言葉が1つでも残っていたら、書き出しの検査で止める。施主名・社名などの検査（tools.history_check）も書き出しの中で必ず回す。
- 公開の前に必ず：①最後のコードで書き出す ②自動の検査がすべて0件 ③書き出しの中のテストが合格 ④見直し役のサブエージェントが読んで確かめる（名前は書き写さず、場所だけ報告）⑤動画を通しで見る ⑥作者の OK。

- 提出のリポジトリには、開発の履歴（コミット）も日時つきで残す（11/5 作者「全部を掃除して残す」。大会の期間に作った証拠にもなる）。そのままは載せない：各コミットに公開用の掃除（自社の決まり・内部のメモを抜く、名前 →「作者」、会社の呼び名 →「自社」、誤った紹介を消す）をかけ、コミットのメッセージも同じく直す。検査は最後のコミットだけでなく、全コミットのファイルとメッセージにかける。掃除の道具は公開しない（消す言葉の一覧が入るため）。
- 書き出しの道具（tools/make_submission_repo.py）とそのテストは公開しない（11/5）。公開しない言葉の一覧が入っていて、文字を分けて書いても、つなげば読めるため。書き出しの検査で「残っていないか」も確かめる。

## 画面：印刷前の仕上げ用ソフトの作り（2026-11-05 作者「Bambu Studio・Blender・Adobe・CAD のような、Web アプリではない感じに」）
- 決めたこと：
  - 上に「ファイル」のメニュー（新しく読み込む・過去の物件を開く・最近の物件・保存・印刷・閉じる・環境設定）と、作業のタブ（模型・修正・検品・印刷・会社ルール）。タブを替えると、上の道具の帯と右の欄がそのタブの物に替わる。真ん中の 3D／平面図はそのまま。
  - 左は部品と部材の一覧（目のボタンで表示を切り替える）。下の帯に、保存の時刻・縮尺・造形範囲・部品の数・AI のつなぎ方。
  - 色は炭の灰の3段と細い線。アクセントは金（造形板の色）の1つだけ。光らせた部材は赤紫で、3D・平面図・左の一覧・指摘のカードでそろえる。重さは色と字の両方で示す（色だけに頼らない）。
  - 字は Windows の画面の字で 12〜13px。数字は桁をそろえる。大きな見出しは使わない。長い説明は「？」と「くわしく」の中へ移した（消していない）。
  - 動きは、人が押したことへの答えだけ（メニュー・小窓・部材へカメラが寄る 0.4 秒）。動きを減らす設定のときは、すぐに切り替える。
  - 小窓は、外側を押しても閉じない（読み込みの入力を失わない）。Esc・×・やめるで閉じる。
  - 3D／平面図の切り替えは 3D の画面の左上（どのタブからも切り替えられる）。視点のボタンは「模型」タブの帯と、右上の向きの印。同じボタンを2組並べない。
  - 前の画面の機能は1つもなくしていない（置き場所を変えただけ。見え方の切り替えは、約束どおり起動のモードに置きかえた）。
- 理由：多機能でも、すっきり見せるため。どの道具がどのタブのものかを、選んだタブと道具の帯が同じ面でつながることで分かるようにした。
- 弱い点 (要検証)：切妻などの大屋根の指摘で光るのは軒の縁だけ（部材の形の一覧に屋根全体の形がない）。「新しく読み込む」→ 組み立て → 開く の成功の流れは、本物の glb ではまだ確かめていない。
